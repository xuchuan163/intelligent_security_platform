# 11 Phase 2 NL2SQL Candidate Generation Design

## Scope

Phase 2 Task 2.3-C only. This slice designs the internal natural-language-to-candidate-SQL capability.

The goal is to turn a user question into a candidate SQL string that can be audited by the existing 2.3-A SQL safety gate and, only after passing audit, optionally executed by the existing 2.3-B read-only executor.

## Current Preconditions

- 2.3-A is complete: SQL AST audit, table whitelist, field whitelist, tenant/data_scope injection, and `agent_nl2sql_audit`.
- 2.3-B is complete: internal read-only executor runs only audited `sanitized_sql` and writes execution status back to `agent_nl2sql_audit`.
- 2.2 is complete: metric semantic layer exposes catalog, lineage, and aliases that can be used as schema context.

## Design Principles

- Candidate SQL is always untrusted.
- LLM output is never executed directly.
- Audit remains the mandatory boundary between generation and execution.
- Tenant and org scope must not be generated by the LLM; they are injected by the auditor.
- The first implementation should be service-only and testable with a mock LLM.
- No public NL2SQL endpoint is added in this slice.

## Explicit Non-Goals

- No `/api/v1/agent/nl2sql` endpoint.
- No `/api/v1/agent/ask` routing.
- No six-Agent DAG orchestration.
- No automatic execution of unaudited SQL.
- No streaming response.
- No chart generation.
- No 100+ accuracy benchmark in this slice.
- No schema or table expansion beyond the 2.3-A whitelist.

## Recommended Architecture

```text
question
  -> schema context builder
  -> prompt builder
  -> LLM candidate generator
  -> SQL extraction and validation shim
  -> audit_sql(candidate_sql, current_user)
  -> CandidateGenerationResult
```

The 2.3-C service returns both the raw candidate and the audit result. It does not execute the SQL by default. A later caller may explicitly pass audited SQL into the 2.3-B executor, but that caller must remain internal until a separate API review approves external exposure.

## Components

### Schema Context Builder

The schema context builder creates a compact, deterministic prompt context from existing trusted metadata:

- Allowed table names from the 2.3-A whitelist.
- Allowed field names from the 2.3-A whitelist.
- Metric aliases from the 2.2 metric semantic layer when relevant.
- Human-readable table descriptions maintained as static metadata.
- Join hints only for approved table relationships.

The context must not include sensitive fields, blocked tables, audit tables, memory tables, raw identity data, or tenant-specific values.

### Prompt Builder

The prompt builder should produce a strict instruction block:

- Return exactly one MySQL `SELECT` statement.
- Do not return Markdown, prose, comments, code fences, or explanations.
- Do not generate multiple SQL statements.
- Do not use `SELECT *`.
- Use only listed tables and fields.
- Do not include `tenant_id` or `org_path` predicates.
- Do not query audit, memory, authentication, or internal Agent tables.
- Prefer explicit columns and stable aliases.
- Add a conservative `LIMIT` only when the question asks for a list; the auditor will still cap it.
- If the question is ambiguous, return a structured refusal token instead of inventing a query.

### Candidate Generator

The candidate generator is an internal service abstraction. It should support:

- A mock provider for unit tests.
- A Qwen provider for later real integration.
- A deterministic parsing layer that extracts only plain SQL or a known refusal token.
- A timeout and error mapping layer.

The initial TDD implementation should start with the mock provider so tests do not require network access or a real API key.

### Audit Integration

Every generated candidate must be passed to `audit_sql`.

Allowed result:

- Return `status = "audit_passed"`.
- Include `candidate_sql`.
- Include `sanitized_sql`.
- Include `tables_used`, `fields_used`, and `scope_injected`.

Rejected result:

- Return `status = "audit_rejected"`.
- Include `candidate_sql` when available.
- Include `rejection_reason`.
- Do not execute SQL.

No candidate result may claim success unless the auditor allows it.

## Failure Model

The service should normalize failures into stable statuses:

| Status | Meaning | Execution |
|---|---|---|
| `generation_failed` | LLM provider failed, timed out, or returned empty output | No |
| `invalid_output` | Output is not plain SQL or an approved refusal token | No |
| `clarification_required` | The question lacks required business meaning or time range | No |
| `audit_rejected` | SQL was generated but failed 2.3-A audit | No |
| `audit_passed` | SQL was generated and sanitized by audit | Not by 2.3-C |

Ambiguous questions should prefer `clarification_required` over unsafe guessing.

## Candidate SQL Is Untrusted

2.3-C must explicitly treat all generated SQL as hostile input. This applies even when:

- The provider is Qwen.
- The prompt includes table and field constraints.
- The SQL looks syntactically valid.
- The question comes from an admin user.

The only trusted SQL is `sanitized_sql` returned by 2.3-A.

## Testing Design

Add a small generation dataset before the 100+ benchmark:

`backend/tests/datasets/nl2sql_generation_cases.jsonl`

Each case should include:

- `case_id`
- `question`
- `mock_llm_output`
- `expected_status`
- `expected_tables`
- `expected_fields`
- `expected_contains`
- `forbidden_contains`
- `requires_clarification`

Initial test categories:

- Valid project list question.
- Valid worker profile question.
- Valid hazard/work-order question.
- Metric alias question using 2.2 aliases.
- Ambiguous time-range question.
- Output with Markdown code fences.
- Output with explanation text.
- SQL that attempts `tenant_id` override.
- SQL that attempts blocked table access.
- SQL that attempts sensitive field access.
- Multi-statement output.
- Empty LLM output.

## Acceptance Criteria

- A design-only document exists for 2.3-C before implementation starts.
- No backend implementation files are changed in this design step.
- No API endpoint is added.
- The future 2.3-C-A/B implementation can be tested without network access.
- Generated SQL must always flow through 2.3-A audit before being considered usable.
- 2.3-C never executes SQL by itself.

## Planned TDD Slices

### 2.3-C-A: Prompt and Schema Context

Red tests first:

- Build context from the existing whitelist.
- Exclude blocked tables and sensitive fields.
- Include metric alias hints.
- Render prompt with strict output constraints.
- Ensure prompt says not to generate `tenant_id` or `org_path`.

Implementation target:

- `backend/app/services/nl2sql/schema_context.py`
- `backend/app/services/nl2sql/prompt_builder.py`
- `backend/tests/services/test_nl2sql_prompt_builder.py`

### 2.3-C-B: Candidate Generation Service

Red tests first:

- Mock provider returns valid SQL and the service audits it.
- Mock provider returns Markdown and the service rejects it as `invalid_output`.
- Mock provider returns unsafe SQL and the service returns `audit_rejected`.
- Mock provider fails and the service returns `generation_failed`.
- Ambiguous question returns `clarification_required`.

Implementation target:

- `backend/app/services/nl2sql/generator.py`
- `backend/tests/services/test_nl2sql_generator.py`
- `backend/tests/datasets/nl2sql_generation_cases.jsonl`

## Next Review Gate

After 2.3-C-A/B passes tests, review whether to proceed to 2.3-C-C Qwen integration. Do not expose `/api/v1/agent/nl2sql` until a separate endpoint contract, permission model, and user-facing failure behavior are approved.
