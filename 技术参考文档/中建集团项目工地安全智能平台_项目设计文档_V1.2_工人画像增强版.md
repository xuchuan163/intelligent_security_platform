5. 增补用户画像与工人安全评分模型，强调可解释、可申诉、非惩罚性使用。
6. 增补基于贝叶斯网络的事故风险预测与事故原因归因分析方案。
7. 增补隐患整改闭环、重大隐患动态清零、分包商安全评价、个性化安全培训等核心业务场景。
8. 增补数据治理、模型治理、接口扩展、安全合规、MVP 建设路线及验收指标。
9. 将工人画像核心维度明确为安全考核成绩、违规行为、年龄因素、体检健康状况，并加入工种与作业场景修正因子。
10. 增补工人危险等级评分模型、权重设计、强规则触发器和可解释输出模板。
11. 增补事故案例导入、案例标签体系、历史案例回测和权重优化机制，用于验证算法合理性。
12. 增补工人画像相关数据库表、Agent 联动方式与健康/年龄数据合规使用边界。

# 1. 项目概述

## 1.1 项目背景

随着建筑行业安全生产监管要求不断提升，传统依赖人工巡检、纸质台账、经验判断和事后整改的安全管理模式，已难以满足大型工程项目群、跨区域项目和多分包协同管理的需要。中建集团作为大型建筑央企，项目数量多、作业类型复杂、参建单位众多、人员流动性强，安全生产管理面临以下挑战：

1. **数据分散**：隐患、人员、设备、培训、视频、审批、事故案例等数据分布在不同系统中，缺少统一的数据底座。
2. **隐患闭环效率不高**：隐患发现、派单、整改、复查、销号、复盘存在人工流转慢、责任追踪难、重复隐患识别弱等问题。
3. **安全分析偏静态**：多数系统以台账统计和报表展示为主，对隐患成因、风险传播路径、事故概率预测支撑不足。
4. **知识利用不足**：安全规范、集团制度、施工方案、事故案例、整改经验等知识沉淀在文档中，现场人员难以及时调用。
5. **培训缺乏个性化**：安全教育往往采用统一题库和统一课件，难以针对工种、岗位、行为风险和历史错题精准推送。
6. **智能化应用割裂**：视频 AI、问答机器人、报表工具、业务审批系统之间缺少智能协同，尚未形成完整的安全智能体生态。

因此，本项目拟建设“中建集团项目工地安全智能平台”，通过大语言模型 LLM、智能问数 NL2SQL、RAG 检索增强生成、知识图谱、贝叶斯归因、计算机视觉和多 Agent 协同，打造覆盖项目工地安全管理全流程的智能管控平台。

## 1.2 项目定位

本项目不应仅定位为“安全问答系统”或“报告生成工具”，而应定位为：

> **面向施工现场安全生产全过程的智能管控平台，以安全隐患闭环为主线，以四库协同为数据底座，以多 Agent 协同为执行框架，以知识图谱和贝叶斯网络为推理核心，实现问数、查因、预警、整改、培训、评价和报告的一体化智能管理。**

## 1.3 建设目标

1. **实现安全数据自然语言问数**：支持集团、区域、项目多级用户通过自然语言查询隐患、整改、培训、人员、设备、分包商等安全指标。
2. **实现隐患整改智能闭环**：支持隐患识别、分类、定级、责任主体识别、整改措施生成、派单、提醒、复查、销号和归档。
3. **实现安全报告自动生成**：支持日报、周报、月报、专项检查报告、事故分析报告、领导驾驶舱简报等自动生成。
4. **实现工人安全画像与风险评分**：融合培训、证书、体检、违规、隐患关联、作业风险等数据，形成可解释的个人安全风险画像。
5. **实现分包商安全评价**：从隐患表现、整改效率、培训覆盖、事故险情、人员稳定性等维度评价分包商安全履约能力。
6. **实现事故贝叶斯归因分析**：构建人、机、料、法、环、管多因素因果网络，支持事故风险预测和事故原因反向推理。
7. **实现个性化安全培训与出题**：按工种、作业场景、隐患类型、历史错题和近期风险生成差异化题目。
8. **实现现场智能感知联动**：结合视频识别、门禁实名制、设备物联、移动端随手拍等数据，提升现场安全态势感知能力。

## 1.4 适用范围

本系统适用于中建集团下属工程局、区域公司、子公司、项目部及分包单位的安全生产管理工作，覆盖房建、市政、基础设施、工业厂房、装饰装修、机电安装等各类工程场景。

| 用户角色 | 主要诉求 | 典型功能 |
|---|---|---|
| 集团管理层 | 看全局安全态势、重大风险、项目排名 | 领导驾驶舱、风险预警、月度分析 |
| 区域公司/工程局 | 管辖项目横向对比、重点项目督办 | 项目排名、重大隐患跟踪、分包商评价 |

# 2. 业务目标与建设原则

## 2.1 总体业务目标

平台建设应围绕“事前预防、事中管控、事后复盘、持续改进”的安全管理闭环展开。

```text
事前：安全培训、风险识别、作业准入、风险预警
事中：现场识别、隐患发现、整改派单、过程督办
事后：事故归因、责任链分析、报告生成、案例沉淀
持续：画像评分、分包评价、知识更新、模型迭代
```

## 2.2 建设原则

1. **业务闭环优先**：所有 AI 能力都应服务于隐患整改、风险预警、培训提升和事故预防，不做孤立的“炫技型 AI”。
2. **数据可信优先**：MySQL 作为结构化事实主库，所有业务结论应可追溯到原始数据、流程单据、图片或规范条款。
3. **人机协同优先**：AI 可生成建议、初判等级、推荐措施，但重大隐患定级、责任认定、处罚建议等必须保留人工确认。
4. **可解释优先**：评分、预警、归因、报告中的关键结论必须说明数据来源、判断依据和影响因素。
5. **权限隔离优先**：集团、区域、项目、分包、班组、个人等角色按最小权限访问数据。
6. **渐进建设优先**：先建设高价值 MVP，再逐步扩展复杂模型和自动化能力。

# 3. 系统总体架构

## 3.1 五层总体架构

系统建议采用五层架构：

```text
┌────────────────────────────────────────────┐
│ 应用层：问数、隐患整改、报告、培训、评分、预警、审批 │
├────────────────────────────────────────────┤
│ Agent 编排层：主控 Agent、专项 Agent、工具调用、权限控制 │
├────────────────────────────────────────────┤
│ 智能能力层：LLM、NL2SQL、RAG、KG 推理、贝叶斯、CV │
├────────────────────────────────────────────┤
│ 数据服务层：MySQL + Neo4j + Milvus + Redis + 对象存储 │
├────────────────────────────────────────────┤
│ 数据采集层：实名制、隐患、设备、视频、门禁、BIM、IoT │
└────────────────────────────────────────────┘
```

## 3.2 架构层次说明

| 层次 | 组件 | 功能说明 |
|---|---|---|
| 用户交互层 | 企业微信、移动 APP、Web 端、监控大屏、驾驶舱 | 提供多端统一访问入口 |
| 应用服务层 | 问数、整改、报告、培训、预警、审批、画像 | 封装业务流程与页面服务 |
| Agent 编排层 | Agent Orchestrator、任务路由、工具管理、权限网关 | 调度多 Agent 协作，控制工具调用与输出审查 |
| 智能能力层 | LLM、NL2SQL、RAG、知识图谱、贝叶斯网络、CV | 提供理解、生成、检索、推理、识别能力 |
| 数据服务层 | MySQL、Neo4j、Milvus、Redis、对象存储、消息队列 | 支撑结构化、关系、向量、缓存、附件和异步任务 |
| 数据采集层 | 劳务实名制、隐患系统、巡检 APP、视频 AI、设备物联、审批系统 | 汇聚现场生产安全数据 |
| 基础设施层 | 私有云、容器平台、GPU、网络安全、日志审计 | 提供算力、存储、网络与安全底座 |

```text
  ↓

  ↓

  ↓

  ↓

  ↓
```

```text
  ↓
```

```text

  ↓

  ↓

```

# 4. 四库协同存储架构

## 4.1 设计原则

四库协同存储架构遵循“按数据特征分库、按业务主线协同、按统一 ID 贯通”的原则：

1. **MySQL 存事实**：结构化业务数据和流程状态以 MySQL 为主数据来源。
2. **Neo4j 存关系**：项目、分包商、班组、人员、隐患、设备、事故等复杂关系存入图数据库。
3. **Milvus 存语义**：安全规范、制度文件、事故案例、整改案例、行为记忆等向量化存储。
4. **Redis 存状态和热点**：会话、缓存、热点指标、Agent 执行状态、限流计数等存入 Redis。
5. **对象存储存附件**：图片、视频片段、报告文件、方案文件、规范原文等存入对象存储。

## 4.2 统一主数据 ID 体系

四库之间必须通过统一 ID 体系打通，避免同一项目、人员、分包商在不同系统中重复编码。

| 主数据对象 | 推荐 ID | 说明 |
|---|---|---|
| 项目 | project_id | 集团统一项目编码 |
| 标段/区域 | zone_id | 项目内区域或楼栋编码 |
| 分包商 | subcontractor_id | 统一社会信用代码或集团供应商编码 |
| 班组 | team_id | 分包商下属班组编码 |
| 人员 | worker_id | 劳务实名制人员唯一编码 |
| 设备 | equipment_id | 设备台账唯一编码 |
| 隐患 | hazard_id | 隐患单唯一编号 |
| 整改任务 | rectification_id | 整改流程单号 |
| 培训记录 | training_record_id | 培训考试记录编号 |
| 事故/险情 | incident_id | 事故或险情事件编号 |
| 规范条款 | rule_id | 法规、标准、制度条款编号 |

## 4.3 MySQL：结构化业务主库

MySQL 存储所有结构化业务事实数据，包括项目、人员、设备、隐患、检查、整改、培训、审批、报告等。

### 4.3.1 核心表设计

```sql
CREATE TABLE safety_hazard (
    hazard_id           VARCHAR(64) PRIMARY KEY COMMENT '隐患ID',
    project_id          VARCHAR(64) NOT NULL COMMENT '项目ID',
    zone_id             VARCHAR(64) COMMENT '区域/楼栋/工区ID',
    location            VARCHAR(255) COMMENT '具体位置',
    hazard_type         VARCHAR(64) COMMENT '隐患类型：高处作业/临电/消防/机械等',
    hazard_level        VARCHAR(32) COMMENT '一般/较大/重大',
    description         TEXT COMMENT '隐患描述',
    source_type         VARCHAR(32) COMMENT '巡检/随手拍/视频AI/设备告警/问答录入',
    discoverer_id       VARCHAR(64) COMMENT '发现人ID',
    responsible_org_id  VARCHAR(64) COMMENT '责任单位ID',
    responsible_team_id VARCHAR(64) COMMENT '责任班组ID',
    responsible_user_id VARCHAR(64) COMMENT '责任人ID',
    status              VARCHAR(32) COMMENT '待派单/待整改/整改中/待复查/已闭环/已驳回',
    required_finish_at  DATETIME COMMENT '要求整改完成时间',
    actual_finish_at    DATETIME COMMENT '实际整改完成时间',
    review_user_id      VARCHAR(64) COMMENT '复查人ID',
    review_result       VARCHAR(32) COMMENT '通过/不通过',
    created_at          DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_project_time(project_id, created_at),
    INDEX idx_type_level(hazard_type, hazard_level),
    INDEX idx_status(status),
    INDEX idx_responsible(responsible_org_id, responsible_team_id)
```

Neo4j 存储安全管理对象之间的关系，用于责任链追溯、风险传播分析、重复隐患识别和分包商表现分析。

### 4.4.1 图谱节点

```cypher

(:Equipment {equipment_id, name, equipment_type, status})

```

### 4.4.2 图谱关系

```cypher
(:Project)-[:HAS_ZONE]->(:Zone)
(:Project)-[:HAS_SUBCONTRACTOR]->(:Subcontractor)
(:Subcontractor)-[:HAS_TEAM]->(:Team)
(:Team)-[:HAS_WORKER]->(:Worker)
(:Worker)-[:PARTICIPATES_IN]->(:Operation)
(:Operation)-[:LOCATED_AT]->(:Zone)
(:Hazard)-[:OCCURRED_AT]->(:Zone)
(:Hazard)-[:RELATED_TO_EQUIPMENT]->(:Equipment)
(:Hazard)-[:RESPONSIBLE_ORG]->(:Subcontractor)
(:Hazard)-[:RESPONSIBLE_TEAM]->(:Team)

```

### 4.4.3 典型图查询

```cypher
-- 查询某项目近30天重复出现高处作业隐患的分包商
MATCH (p:Project {project_id:$project_id})-[:HAS_SUBCONTRACTOR]->(s:Subcontractor)<-[:RESPONSIBLE_ORG]-(h:Hazard)
WHERE h.hazard_type = '高处作业' AND h.created_at >= datetime() - duration('P30D')
RETURN s.name, count(h) AS hazard_count
ORDER BY hazard_count DESC;
```

## 4.7 四库数据同步机制

```text
业务系统写入 MySQL
  ↓
数据变更事件写入消息队列
  ↓
同步服务更新 Neo4j 关系图谱
  ↓
文本内容进入向量化管道写入 Milvus
  ↓
Redis 清理或刷新相关缓存
```

同步策略：

1. **强一致场景**：隐患状态、整改状态、审批状态以 MySQL 为准，更新后立即刷新缓存。
2. **最终一致场景**：图谱关系和向量索引允许分钟级延迟。
3. **批处理场景**：历史事故案例、规范文档、报告模板可采用离线批量向量化。
4. **变更追踪**：所有跨库同步任务需记录 source_id、target_type、sync_status、retry_count 和 error_message。

# 5. 数据治理与安全指标语义层

## 5.1 数据治理目标

平台成败不只取决于模型能力，更取决于安全数据是否标准、完整、可信和可追溯。建议优先建设统一数据治理体系。

## 5.2 基础字典

| 字典 | 说明 |
|---|---|
| 项目字典 | 项目编码、项目名称、区域、业态、阶段、责任单位 |
| 分包商字典 | 企业名称、统一社会信用代码、资质、合同、评价等级 |
| 人员字典 | 实名制 ID、工种、班组、证书、进退场状态 |
| 设备字典 | 设备编号、类型、状态、维保周期、责任人 |
| 隐患分类字典 | 高处作业、临电、消防、机械、深基坑、脚手架等 |
| 事故类型字典 | 高处坠落、物体打击、触电、坍塌、火灾、机械伤害等 |
| 风险因素字典 | 人、机、料、法、环、管六类因素 |
| 规范条款字典 | 规范名称、条款号、适用场景、强制性、风险等级 |
| 指标口径字典 | 隐患整改率、重大隐患闭环率、违章率、培训合格率等 |
| 权限字典 | 集团、区域、项目、分包、班组、个人权限范围 |

## 5.3 安全指标语义层

NL2SQL 的稳定性依赖统一指标口径。建议在数据库之上建设“安全指标语义层”，由业务专家确认指标定义。

| 指标名称 | 计算口径 | 维度 | 说明 |
|---|---|---|---|
| 隐患总数 | count(hazard_id) | 项目、区域、类型、等级、时间 | 统计期内新发现隐患 |
| 隐患整改率 | 已闭环隐患数 / 应整改隐患数 | 项目、分包商、班组 | 不含已撤销或误报隐患 |
| 重大隐患闭环率 | 已闭环重大隐患 / 重大隐患总数 | 项目、区域 | 用于重点督办 |
| 超期整改率 | 超期完成或未完成隐患数 / 应整改隐患数 | 分包商、项目 | 衡量整改履约 |
| 重复隐患率 | 重复出现同类隐患数 / 隐患总数 | 类型、区域、班组 | 衡量根因治理效果 |
| 培训合格率 | 通过培训人数 / 应培训人数 | 工种、班组、项目 | 衡量培训覆盖和效果 |
| 班组违章率 | 班组违章次数 / 班组出勤人日 | 班组、分包商 | 归一化后用于横向对比 |
| 分包商安全评分 | 隐患、整改、培训、事故、处罚综合得分 | 分包商 | 用于分包评价 |

## 5.4 数据质量规则

1. 隐患必须包含项目、位置、类型、等级、责任单位、状态、创建时间。
2. 整改任务必须绑定唯一隐患编号。
3. 工人画像评分所用数据必须保留来源和更新时间。
4. 事故归因分析必须绑定事故事件、相关隐患、作业类型和风险因素。
5. 文档入库必须记录来源、版本、适用范围、生效时间和失效时间。
6. 所有指标结果需可追溯到明细数据和计算口径。

# 6. 多 Agent 体系设计

## 6.1 设计思路

系统采用“主控 Agent + 专项 Agent + 工具层”的多 Agent 协同模式。

```text
用户请求
  ↓
主控 Agent：意图识别、权限校验、任务拆解、路由决策
  ↓
专项 Agent：问数、整改、报告、培训、预警、归因、审批、知识库
  ↓
工具层：SQL、Cypher、向量检索、贝叶斯推理、CV、流程引擎、消息推送
  ↓
结果汇总、解释生成、审计记录
```

## 6.2 Agent Orchestrator 主控智能体

主控 Agent 是所有用户请求的统一入口，负责：

1. 识别用户意图：问数、查知识、生成报告、创建整改任务、事故归因等。
2. 校验用户权限：项目范围、数据范围、功能范围、敏感字段访问权限。
3. 拆解复杂任务：将综合问题拆成 SQL 查询、图谱查询、RAG 检索、归因分析和报告生成子任务。
4. 调用合适工具：选择 NL2SQL、Cypher、Milvus 检索、贝叶斯模型、CV 服务、流程引擎等。
5. 控制输出风险：对模型输出进行事实校验、敏感信息脱敏和人工确认提示。
6. 记录审计日志：保留问题、调用工具、生成结果、数据来源和操作人。

## 6.3 智能问数 Agent

智能问数 Agent 面向管理层、安全员和项目人员，支持自然语言查询安全业务数据。

### 6.3.1 典型问题

- “本周哪个项目隐患最多？”
- “A 项目重大隐患闭环率是多少？”
- “近 30 天高处作业隐患趋势如何？”
- “哪个分包商整改超期最多？”
- “三工区今天还有哪些隐患未闭环？”
- “本月各班组培训合格率排名是多少？”

### 6.3.2 核心能力

1. 指标识别：理解“整改率”“闭环率”“超期率”等业务指标。
2. 时间解析：支持今天、本周、本月、近 30 天、春节前后等时间表达。
3. 范围解析：识别集团、区域、项目、楼栋、工区、分包商、班组。
4. SQL 安全生成：只允许 SELECT 查询，自动加权限过滤条件。
5. 结果解释：将查询结果转为自然语言、表格或图表。
6. 追问建议：根据结果给出下一步分析问题，如“是否查看超期原因？”

## 6.4 隐患整改 Agent

隐患整改 Agent 是平台核心业务 Agent，负责将隐患从发现到销号形成闭环。

### 6.4.1 输入来源

| 来源 | 示例 |
|---|---|
| 人工巡检 | 安全员在移动端录入隐患 |
| 工人随手拍 | 工人上传图片和文字描述 |
| 视频 AI | 检测未戴安全帽、未穿反光衣、危险区域入侵 |
| 设备告警 | 塔吊、升降机、临电设备异常 |
| 问答录入 | 用户通过自然语言描述隐患 |

### 6.4.2 处理流程

```text
隐患输入
  ↓
图片/文本解析
  ↓
隐患类别识别
  ↓
风险等级建议
  ↓
规范条款与相似案例召回
  ↓
责任单位、班组、人员识别
  ↓
整改措施、期限、复查要点生成
  ↓
派单或提交人工确认
  ↓
整改跟踪、超期提醒、复查验收
  ↓
闭环归档、案例入库、画像更新
```

### 6.4.3 输出示例

```text
隐患类别：高处作业 / 临边防护
风险等级建议：高风险，建议按较大隐患处理
责任主体建议：外架分包单位、三工区责任班组
整改措施：
1. 立即停止该区域临边高处作业；
2. 按要求设置连续、牢固的临边防护栏杆和踢脚板；
3. 检查作业人员安全带佩戴和高挂低用情况；
4. 由安全员复查通过后恢复作业。
整改期限建议：立即整改，24 小时内闭环。
复查要点：防护是否连续、固定是否牢靠、人员 PPE 是否合规。
依据来源：相似隐患案例、项目安全管理制度、相关规范条款。
```

## 6.5 报告生成 Agent

### 6.5.1 报告类型

| 报告类型 | 使用对象 | 内容重点 |
|---|---|---|
| 项目安全日报 | 项目部 | 当日隐患、整改、作业、告警、明日风险 |
| 项目安全周报 | 项目经理、安全总监 | 周趋势、分包排名、重点隐患、整改闭环 |
| 月度安全分析报告 | 区域/集团 | 月度 KPI、风险趋势、项目排名、管理建议 |
| 专项检查报告 | 安全部门 | 脚手架、临电、消防、深基坑、起重机械专项 |
| 事故/险情分析报告 | 管理层 | 经过、原因、责任链、防范措施、类似案例 |
| 领导驾驶舱简报 | 集团/区域领导 | 重点项目、重大隐患、预警事项、督办建议 |

### 6.5.2 报告生成原则

1. 结论必须有数据来源。
2. 异常指标必须说明统计口径和时间范围。
3. 管理建议应区分立即整改、限期整改、制度优化和培训提升。
4. 正式报告中的事故责任、处罚建议必须标注“需人工审核”。

场景化出题 Agent 用于生成个性化安全培训题库。

| 事故案例 | 结合集团或行业典型事故生成警示题 |
| 作业任务 | 当日动火、高处、吊装作业前推送专项题 |

### 6.6.2 题型

1. 单选题
2. 多选题
3. 判断题

6. 事故案例复盘题

## 6.7 风险预警 Agent

风险预警 Agent 每日或实时扫描项目风险，发现异常后自动推送。

### 6.7.1 预警规则

| 预警类型 | 触发条件示例 |
|---|---|
| 重大隐患预警 | 重大隐患超过整改期限仍未闭环 |
| 重复隐患预警 | 同区域或同班组 7 天内重复出现同类隐患 |
| 分包商风险预警 | 分包商整改率低于阈值且隐患数量上升 |
| 人员风险预警 | 工人培训不合格且参与高危作业 |
| 设备风险预警 | 设备维保超期或多次告警 |
| 天气环境预警 | 大风、暴雨、高温条件下存在高危作业 |

## 6.8 事故归因 Agent

事故归因 Agent 结合 MySQL 事实数据、Neo4j 关系链、Milvus 案例库和贝叶斯网络，对事故或险情进行概率归因。

主要能力：

1. 关联事故发生前的隐患、作业、人员、设备、天气和管理数据。
2. 识别可能原因因素并给出概率排序。
3. 检索相似事故案例和规范条款。
4. 生成事故分析报告初稿。
5. 提出防范措施和复盘培训题。

## 6.9 分包商评价 Agent

分包商评价 Agent 从项目群维度分析分包商安全表现。

| 评价维度 | 指标 |
|---|---|
| 隐患表现 | 隐患数量、重大隐患数、重复隐患率 |
| 整改表现 | 整改及时率、复查通过率、超期整改率 |
| 培训表现 | 培训覆盖率、考试通过率、错题集中类型 |
| 事故险情 | 险情数、事故数、处罚记录 |
| 人员稳定性 | 工人流动率、持证率、特种作业人员合规率 |
| 协同表现 | 响应速度、整改质量、主动上报隐患数量 |

## 6.10 安全知识库 Agent

# 8. 智能问数 NL2SQL 实现方案

## 8.1 设计目标

NL2SQL 能力用于将用户自然语言问题转换为安全可控的 SQL 查询。企业生产环境中，NL2SQL 不能直接裸生成 SQL，必须配套指标语义层、权限控制、SQL 审查和结果校验。

## 8.2 处理流程

```text
用户问题
  ↓
意图识别：问指标、问明细、问趋势、问排名、问原因
  ↓
权限校验：用户可访问项目、字段和数据范围
  ↓
语义层解析：指标、维度、时间、过滤条件
  ↓
Schema 召回：只召回相关表和字段
  ↓
SQL 生成：只生成 SELECT
  ↓
SQL 安全检查：语法、权限、耗时、敏感字段
  ↓
SQL 执行：只读账号、查询超时控制
  ↓
结果校验：空值、异常值、口径提示
  ↓
自然语言解释和图表展示
```

## 8.3 SQL 安全规则

1. 仅允许 SELECT 查询。
2. 禁止 UPDATE、DELETE、INSERT、DROP、ALTER、TRUNCATE。
3. 禁止访问系统表和未授权表。
4. 自动追加项目权限过滤条件。
5. 限制返回行数，默认 LIMIT 1000。
6. 查询超时自动终止。
7. 敏感字段如身份证号、手机号、体检结论、人脸特征默认脱敏。
8. 高风险统计口径必须展示指标定义。
9. SQL、结果和回答均写入审计日志。

## 8.4 Prompt 模板

```text
你是中建集团工地安全平台的 SQL 生成助手。

任务：根据用户问题、指标语义层和数据库 Schema，生成安全、只读、可执行的 MySQL SELECT 查询。

用户问题：{user_question}
用户权限范围：{permission_scope}
指标定义：{metric_definition}
可用 Schema：{schema_description}

要求：
1. 只能生成 SELECT 查询。
2. 必须包含权限过滤条件 project_id IN (...权限范围...)。
3. 不允许查询敏感字段，确需展示时必须使用脱敏字段。
4. 时间表达必须转换为明确日期范围。
5. 返回结果需适合后续自然语言解释。
6. 只输出 SQL，不输出解释。
```

## 8.5 示例

用户问题：

```text
近30天哪个分包商高处作业隐患最多？
```

生成 SQL：

```sql
SELECT
    responsible_org_id,
    COUNT(*) AS hazard_count
FROM safety_hazard
WHERE hazard_type = '高处作业'
  AND created_at >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)
  AND project_id IN (${authorized_project_ids})
GROUP BY responsible_org_id
ORDER BY hazard_count DESC
LIMIT 10;
```

回答示例：

```text
近30天高处作业隐患数量排名前列的责任单位为：A 分包商 18 起、B 分包商 11 起、C 分包商 8 起。统计口径为：隐患类型=高处作业，时间范围=近30天，按责任单位汇总。建议进一步查看 A 分包商相关隐患是否集中在同一班组或同一区域。
```

# 9. RAG 安全知识库实现方案

## 9.1 知识来源

1. 国家法律法规。
2. 行业规范标准。
3. 住建系统安全管理要求。
4. 集团安全管理制度。
5. 项目施工组织设计、专项施工方案、应急预案。
6. 危大工程方案和专家论证资料。
7. 历史隐患案例。
8. 事故案例和处罚通报。
9. 培训课件和题库。

## 9.2 文档入库流程

```text
文档上传
  ↓
文档解析：PDF/Word/Markdown/HTML/图片 OCR
  ↓
结构化切分：按章节、条款、表格、图示切块
  ↓
元数据标注：来源、版本、生效日期、适用场景、条款号
  ↓
向量化：生成 embedding
  ↓
写入 Milvus
  ↓
同步规范条款节点到 Neo4j
  ↓
人工抽检和版本发布
```

## 9.3 检索策略

1. 向量检索：召回语义相似内容。
2. 关键词检索：保证条款号、规范名称、专有名词准确匹配。
3. 图谱扩展：根据隐患类型、事故类型、作业场景扩展相关条款。
4. 重排序：按相关性、时效性、权威等级、适用场景排序。
5. 引用约束：回答中必须标注知识来源、条款号或文档标题。

## 9.4 回答质量控制

1. 检索不到依据时，不应编造条款。
2. 规范条款存在版本冲突时，应提示版本差异。
3. 对重大隐患、事故责任、处罚建议，需提示人工审核。
4. 输出整改建议时，应区分“规范要求”“平台建议”“需现场确认事项”。

# 10. 工人画像与危险等级评定模型

## 10.1 设计定位

工人画像模块是本平台“事前预防”和“精准培训”的核心能力之一。该模块不应被设计为单纯的“处罚分”或“个人信用分”，而应定位为：

> **面向施工现场作业安全的个人风险识别、培训干预、作业适配和管理辅助工具。**

其核心目标包括：

1. **提前识别高风险人员**：结合安全考核、违规行为、年龄阶段、体检健康状况、作业环境等因素，识别可能存在较高作业风险的人员。
2. **辅助高危作业准入**：在高处作业、动火作业、起重吊装、有限空间、深基坑、夜间施工等高风险场景下，为安全员提供人员准入建议。
3. **精准推送安全培训**：根据工人的薄弱项、历史错题、违规类型和健康适配情况，自动推荐专项培训和个性化题目。
4. **支撑班组与分包商管理**：将个人风险画像向班组、分包商、项目维度聚合，用于识别管理薄弱环节。
5. **通过事故案例验证模型合理性**：导入历史事故、险情和典型隐患案例，对评分规则、权重和等级阈值进行回测与优化。

需要强调的是，工人危险等级评定应服务于“提醒、培训、复核和预防”，不能作为处罚、辞退、歧视性管理或责任认定的唯一依据。

---

## 10.2 工人画像核心维度

结合当前项目设计，本版本建议将工人画像核心维度确定为四大类：**安全考核成绩、违规行为、年龄因素、体检健康状况**。同时，为了提升模型解释性和业务适用性，建议增加“工种与作业场景”作为修正因子，而不是单独作为惩罚项。

| 一级维度 | 二级指标 | 数据来源 | 主要作用 | 注意事项 |
|---|---|---|---|---|
| 安全考核成绩 | 三级安全教育成绩、专项培训成绩、考试通过率、错题类型、复训次数 | 培训系统、考试系统 | 反映安全知识掌握水平和学习能力 | 考核成绩低不等于一定高风险，应结合行为数据判断 |
| 违规行为 | 未戴安全帽、未系安全带、违章动火、临电违规、进入危险区域、视频 AI 告警、人工巡检违规记录 | 隐患系统、视频 AI、巡检系统、移动端随手拍 | 反映现场行为风险，是评分中最重要的动态因素 | 需区分个人违规、班组管理问题和现场条件问题 |
| 年龄因素 | 年龄段、岗位适配性、连续作业强度适配性 | 劳务实名制系统 | 用于作业适配和风险提醒 | 年龄不应被简单作为扣分项，应采用分段、温和、辅助性权重 |
| 体检健康状况 | 体检是否有效、是否存在作业限制、高血压/眩晕/视力/听力等与岗位相关的体检结论、复检状态 | 体检系统、入场资料 | 用于判断是否适合高处、吊装、夜间、有限空间等作业 | 健康数据高度敏感，应脱敏、最小化展示，仅用于安全适配 |
| 工种与作业场景修正因子 | 高处作业、动火作业、起重吊装、有限空间、临电作业、夜间施工、交叉作业 | 作业票、班组排班、项目计划 | 根据作业风险调整阈值和预警等级 | 不建议直接作为个人扣分项，应作为风险暴露系数 |

### 10.2.1 四类核心维度的业务解释

1. **安全考核成绩**  
   反映工人对安全规程、岗位风险、应急处置和项目制度的掌握情况。适合用于识别“知识型风险”，例如不知道高处作业安全带使用要求、不熟悉动火审批流程、不清楚临电三级配电两级保护要求等。

2. **违规行为**  
   反映工人在现场真实作业中的行为表现，是最能体现短期风险变化的维度。违规行为应按严重程度、发生频率、是否重复、是否发生在高危作业场景中进行差异化计分。

3. **年龄因素**  
   年龄本身不应被视为风险标签，但在施工场景中，部分作业对体力、反应速度、夜间适应性、连续作业能力存在要求。因此，年龄应作为“作业适配修正因子”，主要用于提示是否需要加强班前确认、缩短连续作业时长或避免安排特别高风险作业。

4. **体检健康状况**  
   体检数据应重点服务于“人岗匹配”。例如，存在眩晕、高血压未控制、视力或听力不满足岗位要求等情况时，应提示安全员谨慎安排高处作业、起重信号指挥、夜间作业或有限空间作业。

## 10.3 工人危险等级评分模型

建议采用“**基础风险分 + 动态行为分 + 作业场景修正 + 人工复核**”的方式，而不是一次性给出绝对结论。

### 10.3.1 总体评分思路

平台可将工人风险评分定义为 0-100 分，其中分数越高表示风险越高。为了便于管理，也可以同步转换为低风险、中风险、中高风险、高风险四个等级。

```text
工人风险分 R = 
安全考核风险分 A × 25%
+ 违规行为风险分 V × 40%
+ 年龄适配风险分 G × 10%
+ 体检健康适配风险分 H × 20%
+ 作业场景风险修正 S × 5%
```

> 初始建议：违规行为权重最高，体检健康和安全考核次之，年龄因素权重最低，作业场景作为修正项。后续可通过事故案例回测和专家评审动态调整。

### 10.3.2 推荐权重设置

| 维度 | 建议权重 | 设计理由 |
|---|---:|---|
| 违规行为风险分 V | 40% | 直接反映现场真实行为，是短期事故风险的重要信号 |
| 安全考核风险分 A | 25% | 反映安全知识掌握情况，是培训干预的重要依据 |
| 体检健康适配风险分 H | 20% | 影响高处、夜间、吊装、有限空间等作业适配性 |
| 年龄适配风险分 G | 10% | 仅作为辅助修正，避免形成年龄歧视或简单化判断 |
| 作业场景风险修正 S | 5% | 根据当前是否参与高危作业进行动态增强 |

### 10.3.3 各维度分值计算建议

#### 一、安全考核风险分 A

安全考核可按最近一次考试成绩、近 3 次平均成绩、专项培训是否通过、错题类型综合计算。

| 考核表现 | 风险分建议 |
|---|---:|
| 最近 3 次考试均 ≥ 90 分 | 0-10 |
| 最近 3 次平均 80-89 分 | 10-25 |
| 最近 3 次平均 70-79 分 | 25-45 |
| 最近一次低于 70 分或专项培训未通过 | 45-70 |
| 多次未参加培训、考试缺考或高危作业专项培训不合格 | 70-100 |

可进一步识别错题类型，例如：高处作业类错题多，则只在高处作业场景下提高风险提示；临电类错题多，则在临电相关作业中提高提醒等级。

#### 二、违规行为风险分 V

违规行为建议按“严重程度 × 频率 × 时间衰减 × 场景加权”计算。

```text
违规行为风险分 V = Σ（违规严重度分 × 频率系数 × 时间衰减系数 × 场景系数）
```

| 违规类型 | 严重度分建议 | 示例 |
|---|---:|---|
| 轻微违规 | 5-15 | 未按要求佩戴反光衣、一般区域 PPE 不规范 |
| 一般违规 | 15-35 | 未戴安全帽、材料堆放不规范导致通道受阻 |
| 较重违规 | 35-60 | 高处作业未系安全带、临边洞口防护缺失仍作业 |
| 严重违规 | 60-90 | 未审批动火、私拉乱接、擅自进入危险区域 |
| 重大违规 | 90-100 | 无证从事特种作业、违反停工指令继续作业 |

时间衰减建议：

| 发生时间 | 时间衰减系数 |
|---|---:|
| 7 天内 | 1.00 |
| 8-30 天 | 0.80 |
| 31-90 天 | 0.50 |
| 91-180 天 | 0.30 |
| 超过 180 天且未重复发生 | 0.10 |

场景系数建议：

| 场景 | 系数 |
|---|---:|
| 普通作业场景 | 1.00 |
| 高处、动火、吊装、有限空间、临电等高危作业 | 1.20-1.50 |
| 夜间、雨雪大风、高温、交叉作业 | 1.10-1.30 |

#### 三、年龄适配风险分 G

年龄因素建议采用“温和分段 + 作业适配”的方式，不建议直接粗暴扣分。

| 年龄段 | 基础适配风险分建议 | 管理含义 |
|---|---:|---|
| 18-35 岁 | 5-15 | 常规适配，重点关注经验不足和违规行为 |
| 36-50 岁 | 5-20 | 常规适配，重点关注岗位经验和体检状态 |
| 51-55 岁 | 15-30 | 高危作业前加强班前确认和健康确认 |
| 56 岁及以上 | 25-45 | 谨慎安排高强度、高处、夜间和连续作业 |

注意：年龄分不应单独触发高风险等级，只能与体检、违规、作业场景共同作用。

#### 四、体检健康适配风险分 H

体检健康状况建议按“体检有效性 + 岗位禁忌 + 作业限制”计算。

| 体检状态 | 风险分建议 | 管理建议 |
|---|---:|---|
| 体检有效，未见作业限制 | 0-10 | 正常作业 |
| 体检临近过期 | 10-25 | 提醒复检 |
| 体检过期 | 40-70 | 暂缓高危作业，完成复检 |
| 存在需关注指标，但不构成明确禁忌 | 25-50 | 班前健康确认，限制连续高强度作业 |
| 存在岗位禁忌或明确作业限制 | 70-100 | 禁止安排对应高危作业，需人工复核 |

体检健康数据必须进行分级授权。普通班组长可看到“是否适合作业/是否需复核”，不应看到完整医学诊断细节。

#### 五、作业场景风险修正 S

作业场景风险修正用于反映“当前是否处于高风险作业环境”。例如同一个工人在普通地面作业时为中风险，但在 12 层外立面高处作业时可能提升为中高风险。

| 当前作业场景 | 修正建议 |
|---|---:|
| 普通室内/地面作业 | 0-10 |
| 临边洞口附近作业 | 20-40 |
| 高处作业、起重吊装、动火作业、临电作业 | 40-70 |
| 有限空间、深基坑、交叉作业、夜间高危作业 | 60-90 |
| 极端天气下高危作业 | 80-100 |

## 10.4 危险等级划分与管理动作

建议将风险分转换为四级危险等级，并绑定不同管理动作。

| 综合风险分 R | 危险等级 | 等级颜色 | 管理动作 |
|---:|---|---|---|
| 0-29 | 低风险 | 绿色 | 正常作业，常规安全提醒 |
| 30-59 | 中风险 | 黄色 | 推送专项培训题，班前会重点提醒 |
| 60-79 | 中高风险 | 橙色 | 高危作业前需安全员确认，安排复训或复检 |
| 80-100 | 高风险 | 红色 | 暂缓对应高危作业，必须人工复核并制定干预措施 |

### 10.4.1 等级触发规则

除综合评分外，建议增加“强规则触发器”。满足以下条件时，即使综合分未达到高风险，也应强制提升风险等级或触发人工复核：

1. 体检过期且拟参与高危作业；
2. 存在明确岗位禁忌仍被安排对应作业；
3. 最近 7 天发生严重违规；
4. 最近 30 天发生两次及以上同类违规；
5. 未通过高危作业专项培训却申请参与该类作业；
6. 无证或证书过期从事特种作业；
7. 被下达停工或整改要求后仍继续违规作业。

### 10.4.2 输出示例

```text
人员：张三
工种：架子工
所属班组：外架一班组
当前作业：3 号楼 12 层外立面高处作业
综合风险分：72
危险等级：中高风险（橙色）

主要影响因素：
1. 最近 30 天发生 1 次高处作业未系安全带行为，行为风险贡献较高；
2. 高处作业专项培训成绩 68 分，低于项目合格线；
3. 体检有效，但血压指标需关注，建议班前进行健康确认；
4. 当前作业属于高处临边场景，作业风险修正较高。

管理建议：
1. 作业前由安全员进行安全带佩戴和临边防护确认；
2. 当日班前会进行高处作业专项提醒；
3. 推送高处作业专项复训题，复训通过后降低培训风险分；
4. 若 7 日内再次发生同类违规，自动提升为高风险并限制高处作业准入。
```

## 10.5 事故案例导入与算法合理性验证

为了避免评分模型停留在经验判断层面，建议将历史事故案例、险情案例、重大隐患案例导入平台，用于验证和优化工人画像算法。

## 10.5.1 案例数据类型

| 案例类型 | 示例 | 用途 |
|---|---|---|
| 事故案例 | 高处坠落、物体打击、触电、机械伤害、坍塌、火灾 | 验证模型是否能提前识别事故前风险信号 |
| 险情案例 | 人员险些坠落、吊物滑落、临电打火、有限空间异常 | 增加样本量，提升模型敏感度 |
| 重大隐患案例 | 临边防护缺失、动火无审批、设备维保缺失 | 训练风险因子与隐患类型关联 |
| 典型违规案例 | 未戴安全帽、未系安全带、违章指挥、无证作业 | 优化违规行为严重度分 |
| 正向案例 | 主动上报隐患、及时整改、培训优秀 | 防止模型只关注负面行为 |

## 10.5.2 案例标签体系

事故案例导入后，需要进行结构化标签标注，建议包括：

| 标签类别 | 标签内容 |
|---|---|
| 事故类型 | 高处坠落、物体打击、触电、起重伤害、机械伤害、坍塌、火灾 |
| 直接原因 | 未系安全带、临边防护缺失、违章动火、设备失效、误操作 |
| 间接原因 | 培训不足、交底不到位、赶工期、监管缺位、分包管理弱 |
| 人员因素 | 考核不合格、重复违规、健康不适配、无证上岗 |
| 环境因素 | 夜间、雨雪、大风、高温、照明不足、交叉作业 |
| 管理因素 | 隐患未闭环、审批缺失、巡检不到位、整改复查缺失 |
| 后果等级 | 险情、轻伤、重伤、死亡、直接经济损失 |

## 10.5.3 回测验证方法

平台可采用“事故发生前 N 天数据回放”的方式验证算法有效性。

```text
步骤 1：选取历史事故或险情案例。
步骤 2：回溯事故发生前 7 天、30 天、90 天的人员、培训、违规、体检、作业数据。
步骤 3：用当前评分模型计算事故相关人员、班组、分包商的历史风险等级。
步骤 4：观察模型是否在事故发生前给出中高风险或高风险提示。
步骤 5：分析漏报、误报原因，调整权重、阈值或强规则。
```

关键验证指标：

| 指标 | 含义 | 目标建议 |
|---|---|---|
| 召回率 Recall | 已发生事故/险情中，模型提前识别为中高风险或高风险的比例 | 初期优先提高召回率 |
| 精确率 Precision | 被模型判定为高风险的人员中，确实存在高风险证据的比例 | 后续逐步提升 |
| 漏报率 | 事故前未被识别为风险的比例 | 持续降低 |
| 误报率 | 被频繁提示但无明显风险证据的比例 | 控制在可接受范围 |
| 提前预警时间 | 模型在事故前多少天发出有效预警 | 关注 7 天和 30 天窗口 |
| 专家一致性 | 模型判断与安全专家判断的一致程度 | 用于权重校准 |

## 10.5.4 权重优化机制

初始权重可由专家经验设定，后续通过案例回测进行修正。建议采用“三步法”：

1. **专家初始赋权**：由安全总监、项目安全员、信息化团队共同确定初始权重。
2. **历史案例回测**：用事故、险情、重大隐患案例验证权重是否合理。
3. **定期调参复核**：每季度基于新增数据进行模型评估，由专家委员会确认是否调整权重。

可采用的优化方式包括：

- 规则权重人工调整；
- 逻辑回归或评分卡模型辅助校准；
- 贝叶斯网络用于因果概率修正；
- 决策树/随机森林用于发现非线性影响因素；
- SHAP 等解释方法用于识别各因素贡献度。

在项目早期，不建议直接采用完全黑盒模型。更推荐使用“规则评分卡 + 案例回测 + 专家复核”的方式，保证可解释、可落地、可审计。

## 10.7 与多 Agent 的联动设计

| 隐患整改 Agent | 判断隐患责任人或参与人员是否存在重复违规 | 整改建议、复训建议、重点关注人员 |

| 场景化出题 Agent | 根据低分维度、违规类型和事故案例生成题目 | 个性化培训题、错题强化 |
| 报告生成 Agent | 汇总人员风险画像、班组风险和整改措施 | 项目安全周报、分包商评价报告 |
| 事故归因 Agent | 将人员画像作为贝叶斯网络中的“人员因素”证据 | 事故原因概率排序和改进建议 |

## 10.8 合规、伦理与使用边界

工人画像涉及个人信息和健康信息，必须设置清晰边界。

1. **健康信息最小化使用**：体检数据只用于“是否适合作业、是否需要复检、是否存在对应岗位限制”，不在普通页面展示具体诊断细节。
2. **年龄因素谨慎使用**：年龄只作为作业适配和安全提醒因素，不得作为歧视性限制或处罚依据。
3. **人工复核机制**：高风险等级、作业限制建议、健康适配提示必须允许项目安全员和劳务管理员复核。
4. **申诉与更正通道**：工人、班组和分包商可对错误识别、误报违规、过期数据提出申诉。
5. **证据链可追溯**：每个风险结论必须能追溯到考试记录、违规记录、体检状态、作业场景或事故案例。
6. **用途限制**：评分不得作为处罚、辞退、降低工资、差别待遇的唯一依据。
7. **模型定期审计**：定期检查是否存在对年龄、健康状态、特定工种或分包单位的系统性偏差。

# 11. 贝叶斯事故归因与风险预测模型

## 11.1 建设目标

贝叶斯网络用于处理施工安全中的不确定性和多因素因果关系，支持两类能力：

1. **正向预测**：在已知隐患、作业、环境和管理状态下，预测事故风险概率。
2. **反向归因**：在发生事故或险情后，推断最可能的原因因素及其贡献度。

## 11.2 因素体系

建议按“人、机、料、法、环、管”建立事故致因模型。

| 类别 | 风险因素示例 |
|---|---|
| 人 | 培训不足、疲劳作业、无证上岗、违章操作、安全意识弱 |
| 机 | 设备故障、维保缺失、防护装置失效、传感器异常 |
| 料 | 材料堆放混乱、易燃物管理不当、不合格材料 |
| 法 | 方案缺失、交底不到位、作业票不规范、操作规程缺失 |
| 环 | 大风、暴雨、高温、夜间照明不足、交叉作业、场地狭窄 |
| 管 | 监管缺位、分包管理弱、整改不闭环、赶工期、责任不清 |

## 11.3 高处坠落示例网络

```text
培训不足        → 安全带使用不规范
交底不到位      → 风险认知不足
临边防护缺失    → 坠落暴露增加
赶工期          → 违章作业概率上升
监管不到位      → 隐患未及时发现
安全带使用不规范 + 临边防护缺失 + 监管不到位 → 高处坠落风险上升
```

## 11.4 正向预测示例

输入条件：

```text
外立面高处作业；
当日大风；
某分包商近7天整改率低；
班组高处作业培训合格率低；
临边防护隐患尚未闭环。
```

输出：

```text
高处坠落风险等级：高
主要贡献因素：
1. 临边防护隐患未闭环；
2. 高处作业叠加大风环境；
3. 班组培训合格率低；
4. 责任分包商近期整改表现较差。
建议：暂停相关区域高处作业，完成临边防护整改和专项交底后复工。
```

## 11.5 反向归因示例

输入：发生一起高处坠落险情。

输出：

```text
最可能原因排序：
1. 临边防护不到位：42%
2. 安全带使用不规范：31%
3. 现场监管缺位：27%
4. 班前交底不足：21%
5. 作业面照明不足：12%

说明：以上为模型基于事故前隐患、作业、人员、设备和管理数据的概率推断，不等同于正式责任认定，需结合现场调查确认。
```

## 11.6 与四库协同关系

```text
MySQL：提供事故、隐患、整改、作业、培训等事实数据
Neo4j：提供项目、分包商、班组、人员、设备、隐患之间的关系链
Milvus：提供相似事故案例、规范条款和整改经验
Redis：缓存模型计算结果和预警状态
LLM：生成可读的归因解释和整改建议
```

## 11.7 模型建设步骤

1. 由安全专家梳理事故类型和致因因素。
2. 基于历史事故和隐患数据建立初始条件概率表。
3. 通过专家经验补齐低频事故样本不足问题。
4. 在项目运行中持续收集新数据，更新概率参数。
5. 对模型输出进行人工审核和效果评估。
6. 建立模型版本管理，保留每次归因结果所使用的模型版本。

# 12. 计算机视觉与现场感知能力

## 12.1 识别场景

| 场景 | 识别内容 |
|---|---|
| 人员 PPE | 安全帽、反光衣、安全带佩戴 |
| 区域入侵 | 危险区域、吊装半径、临边洞口区域入侵 |
| 高处作业 | 未系安全带、临边作业、脚手架作业 |
| 消防安全 | 消防通道堵塞、烟火识别、灭火器遮挡 |
| 机械设备 | 塔吊、升降机、吊篮、车辆异常靠近 |
| 文明施工 | 材料堆放混乱、裸土覆盖、垃圾堆放 |
| 实名制 | 人脸识别、陌生人告警、进退场记录 |

## 12.2 视频 AI 与隐患 Agent 联动

```text
摄像头视频流
  ↓
边缘端目标检测
  ↓
生成结构化告警事件
  ↓
上传图片/视频片段至对象存储
  ↓
隐患整改 Agent 判断是否生成隐患单
  ↓
责任区域和责任单位识别
  ↓
派单、提醒、复查
```

## 12.3 技术实现建议

1. 边缘端部署轻量目标检测模型，减少视频回传压力。
2. 云端进行告警事件汇总、去重和二次确认。
3. 同一摄像头同一位置短时间内重复告警应合并处理。
4. 视频 AI 结果应作为隐患线索，不宜直接作为处罚依据。
5. 对人脸、视频和行为数据应进行严格权限控制和脱敏展示。

# 14. 安全、合规与模型治理

## 14.1 权限控制

1. 集团用户可查看集团范围数据。
2. 区域/工程局用户仅可查看管辖项目数据。
3. 项目用户仅可查看本项目数据。
4. 分包商仅可查看与自身相关的整改任务和培训数据。
5. 工人仅可查看个人培训、任务、提醒和本人反馈。
6. 敏感数据按字段级权限控制。

## 14.2 数据安全

1. 私有化部署，核心业务数据不出内网。
2. 敏感字段加密存储，包括身份证号、手机号、人脸特征、体检资料等。
3. 接口传输使用 HTTPS 或内网 TLS。
4. 对象存储附件设置访问签名和过期时间。
5. 日志中不得记录明文敏感信息。
6. 数据导出需审批和水印追踪。

## 14.3 模型安全

1. LLM 输出必须经过安全审查和事实校验。
2. 重大隐患等级、事故责任、处罚建议必须人工确认。
3. RAG 回答必须基于检索内容，禁止编造规范条款。
4. NL2SQL 只允许只读查询。
5. 建立 Prompt 注入防护和越权查询防护。
6. 所有模型调用记录输入、输出、工具调用、模型版本和用户信息。

## 14.4 审计追溯

审计日志至少包括：

1. 用户 ID、角色、组织、登录 IP。
2. 请求时间、请求内容、业务对象。
3. Agent 调用链路和工具调用记录。
4. SQL/Cypher 查询摘要。
5. 返回结果摘要。
6. 人工确认记录。
7. 文件导出和外发记录。

## 14.5 人机协同边界

| 场景 | AI 权限 | 人工要求 |
|---|---|---|
| 普通知识问答 | 可直接回答 | 无需审核 |
| 普通问数 | 可直接回答 | 展示口径和来源 |
| 隐患整改建议 | 可生成建议 | 派单前可配置人工确认 |
| 重大隐患定级 | 仅建议 | 必须人工确认 |
| 事故原因归因 | 仅概率分析 | 必须调查组确认 |
| 处罚与责任认定 | 不自动决策 | 必须人工决策 |
| 人员高风险限制 | 仅辅助建议 | 必须管理人员确认 |

# 15. 性能与高可用设计

## 15.1 性能目标

| 场景 | 目标 |
|---|---|
| 普通知识问答 | 3-8 秒内返回 |
| 普通问数 | 3-10 秒内返回 |
| 大屏指标刷新 | 5 秒内完成缓存读取 |
| 隐患智能分析 | 5-15 秒返回建议 |
| 报告生成 | 1-5 分钟内完成，异步通知 |
| 视频告警处理 | 秒级产生结构化事件 |
| 向量检索 | Top-K 检索 1 秒级 |

## 15.2 优化措施

1. MySQL 读写分离、索引优化、冷热分层。
2. Redis 缓存热点指标和问数结果。
3. Milvus 分区索引，按知识类型和项目分区。
4. Neo4j 建立 project_id、worker_id、hazard_id 等索引。
5. Agent 任务异步化，长任务通过队列处理。
6. LLM 支持流式输出，提升用户感知速度。
7. 常用报告模板预聚合指标。
8. 视频 AI 边缘计算，云端只处理事件和片段。

## 15.3 高可用设计

1. MySQL 主从复制与定期备份。
2. Redis Cluster 高可用。
3. Milvus 集群部署，索引定期备份。
4. Neo4j 高可用或定期快照备份。
5. LLM 推理服务多副本部署。
6. Agent 服务无状态化部署。
7. 消息队列持久化，失败任务可重试。
8. 关键接口配置熔断、限流和降级。

## 15.4 降级策略

| 故障场景 | 降级方式 |
|---|---|
| LLM 服务不可用 | 返回模板化提示，保留人工流程 |
| Milvus 不可用 | 使用关键词检索或本地知识库索引 |
| Neo4j 不可用 | 使用 MySQL 关系字段进行基础查询 |
| Redis 不可用 | 直接查询数据库，但限制并发 |
| 视频 AI 不可用 | 保留人工巡检和随手拍上报 |
| NL2SQL 失败 | 提供可选筛选条件或转人工报表 |

# 16. 实施路线与 MVP 建设计划

## 16.1 总体实施阶段

| 阶段 | 周期 | 建设重点 | 交付物 |
|---|---|---|---|
| Phase 0 | 1 个月 | 需求梳理、数据盘点、指标口径确认 | 需求规格、数据字典、指标字典 |
| Phase 1 | 2-3 个月 | 四库底座、知识库、智能问数、报告生成 | MVP 平台、问数 Agent、报告 Agent |
| Phase 2 | 2-3 个月 | 隐患整改闭环、移动端随手拍、RAG 整改建议 | 隐患整改 Agent、知识库 Agent |
| Phase 3 | 2 个月 | 用户画像、场景化出题、分包商评价 | 画像评分、培训 Agent、评价 Agent |
| Phase 4 | 2-3 个月 | 知识图谱、贝叶斯归因、风险预警 | 图谱分析、归因 Agent、预警 Agent |
| Phase 5 | 3 个月 | 视频 AI、设备物联、集团级驾驶舱 | 现场感知联动、集团驾驶舱 |

## 16.2 MVP 推荐范围

建议 MVP 不要一开始覆盖所有场景，优先建设四个最有价值的能力：

### MVP 1：智能问数 Agent

支持查询：

1. 本周/本月隐患总数。
2. 重大隐患闭环率。
3. 分包商隐患排名。
4. 班组整改超期排名。
5. 高处作业、临电、消防等专项隐患趋势。

### MVP 2：隐患整改 Agent

支持：

1. 输入隐患描述自动分类。
2. 推荐风险等级。
3. 生成整改措施。
4. 推荐责任单位和整改期限。
5. 形成整改闭环记录。

### MVP 3：报告生成 Agent

支持：

1. 项目安全日报。
2. 项目安全周报。
3. 月度安全分析报告。
4. 分包商安全评价简报。

### MVP 4：场景化出题 Agent

支持：

1. 按工种生成题目。
2. 按近期隐患生成题目。
3. 按错题生成复训题。
4. 输出题目解析和答案。

## 16.3 关键里程碑

| 里程碑 | 时间 | 标志 |
|---|---|---|
| M1 | 第 1 月 | 完成需求、指标、数据字典和总体设计 |
| M2 | 第 3 月 | 四库架构和知识库初版上线 |
| M3 | 第 4 月 | 智能问数 Agent 和报告 Agent 上线试点 |
| M4 | 第 6 月 | 隐患整改 Agent 和移动端闭环上线 |
| M5 | 第 8 月 | 用户画像、分包评价和出题 Agent 上线 |
| M6 | 第 10 月 | 图谱分析和贝叶斯归因试点上线 |
| M7 | 第 12 月 | 视频 AI 联动和集团驾驶舱上线 |

## 16.4 试点建议

1. 选择 2-3 个数据基础较好的项目作为试点。
2. 优先接入隐患台账、人员实名制、培训记录、分包商信息和项目基础信息。
3. 先做项目级闭环，再扩展到区域级、集团级横向对比。
4. 每周收集安全员和项目经理反馈，快速迭代 Agent 输出质量。
5. 对 NL2SQL 问数建立标准问题集和准确率评测集。
